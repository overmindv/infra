# Размещение пилота Overmindv

Расчет на 50 активных пользователей в день. На стенде проверяем 10 пользователей одновременно и две параллельные проверки решений. Регион, бюджет и цели восстановления пока не утверждены: [OVM-124](https://overmindv.atlassian.net/browse/OVM-124).

## Два сервера

| Узел | Что запускаем | Стартовая конфигурация |
| --- | --- | --- |
| Приложение | Compose: веб-вход, frontend, gateway, сервисы, PostgreSQL, Kafka KRaft, MinIO, ClamAV, мониторинг и sandbox-worker | 6 vCPU, 16 ГБ RAM, 200 ГБ NVMe |
| Исполнитель | Отдельная Linux VM: go-judge и готовые рантаймы Python и Go | 2 vCPU, 4 ГБ RAM, 50 ГБ NVMe |

Оставляем восемь баз сервисов и добавляем постоянную БД Sandbox со своей ролью. Результаты, попытки и outbox не должны пропадать при перезапуске worker. Kubernetes и Redis для пилота не нужны. На оба узла доставляем готовые образы по digest, не собираем стек на VPS ([OVM-165](https://overmindv.atlassian.net/browse/OVM-165)).

Снаружи доступен веб-вход по HTTPS. Администрирование доступно через отдельный закрытый канал. PostgreSQL, Kafka, ClamAV и консоль MinIO не публикуем. Если браузеру нужны подписанные ссылки на файлы, выводим только нужный S3 API через HTTPS, без публичных бакетов.

Worker остается на узле приложения. Он читает Kafka, загружает тесты и передает файлы исполнителю через закрытую сеть. Разрешаем только соединение от worker к API go-judge; трафик шифруем и проверяем клиента на входе. API исполнителя не публикуем в интернет. Runner не получает учетных данных Kafka, PostgreSQL и S3. Для пользовательских процессов запрещаем сеть, доступ к metadata, сокету Docker и каталогам хоста. Эти ограничения нужно проверить на целевой VM до приема пользовательского кода ([OVM-229](https://overmindv.atlassian.net/browse/OVM-229)).

## Память и параллелизм

| Статья на узле приложения | Запас, ГиБ |
| --- | ---: |
| ОС и Docker | 1,25 |
| PostgreSQL, включая Sandbox | 2,75 |
| Kafka, включая память вне JVM heap | 1,50 |
| Сервисы, worker и веб-вход | 2,50 |
| MinIO | 0,75 |
| ClamAV | 4,00 |
| Мониторинг | 0,50 |
| **Итого** | **13,25** |

На 16 ГиБ остается 2,75 ГиБ. Это расчет, а не лимиты контейнеров. У провайдера проверяем фактически доступную память. Узел на 8 ГБ не подходит под этот расчет: только для ClamAV рекомендованы 4 ГиБ, а при обновлении сигнатур память временно растет. Проверяем перезагрузку базы сигнатур на стенде, не выключаем проверку файлов ради экономии. [Требования ClamAV к памяти](https://docs.clamav.net/manual/Installing/Docker.html#memory-ram-requirements).

На runner закладываем 0,75 ГиБ на ОС и Docker, 0,5 ГиБ на go-judge, до 2 ГиБ суммарно на два задания и 0,75 ГиБ запаса при доступных 4 ГиБ. По [профилям Sandbox](https://github.com/overmindv/sandbox/blob/main/configs/limits.yaml) стартовые лимиты: Python 128 МиБ, 2 с CPU и 5 с по настенным часам; Go 512 МиБ, 10 с CPU и 30 с по настенным часам. При расчете берем жесткий максимум 1 ГиБ на задание, так как запрос может поднять лимит. Учитываем память сборки и tmpfs в общем лимите runner.

Начинаем с одного слота. Второй включаем после прогона двух параллельных заданий с холодной Go-сборкой. Лимит действует на runner суммарно, даже если workers несколько. Манифест Go задает `-p 1` и `GOMAXPROCS=2`: на двух ядрах две сборки делят CPU. Ограничиваем очередь, время ожидания, размеры файлов и вывода. Перегрузка не должна превращаться в вердикт об ошибке в решении.

### Локальные замеры

| Проба на Linux amd64 в Docker | Условия | Результат |
| --- | --- | --- |
| Kafka `4.3.1` | Один брокер KRaft, 1 vCPU, лимит 1,5 ГиБ, heap 256-512 МиБ, пустой временный диск | 306-309 МиБ в простое по пяти замерам, пик cgroup около 325 МиБ |
| Go `1.26.11` | `go test -p 2 -c`, пустой кеш, два простых файла, 2 vCPU, лимит 1 ГиБ, без сети | 17,2 с на сборку, 31,7 с CPU, тест прошел, пик cgroup около 381 МиБ |

Kafka измерена без записи под нагрузкой. Go собран напрямую в контейнере, с другим `-p` и без лимита CPU-времени на задание. Стандартные 10 с CPU для холодной сборки не подтверждены: их проверяем отдельно через go-judge на целевой VM.

## Диск и копии

| Статья | Приложение, ГиБ | Runner, ГиБ |
| --- | ---: | ---: |
| ОС и образы текущего и предыдущего релизов | 25 | 20 |
| PostgreSQL и WAL | 35 | 0 |
| Kafka | 12 | 0 |
| MinIO: файлы, тесты, артефакты | 35 | 0 |
| Сигнатуры ClamAV | 5 | 0 |
| Логи и метрики | 10 | 2 |
| Временные файлы, кеши и экспорт | 12 | 13 |
| **Итого** | **134** | **35** |

200 ГБ и 50 ГБ из тарифа дают около 186 и 47 ГиБ. Значения в таблице нужны для расчета запаса; место на диске и рост данных контролируем отдельно. Для старта предлагаем алерт при 70% заполнения и срочную реакцию при 85%.

Пример для Kafka: 500 запусков в сутки, средний запрос 256 КиБ, 7 дней хранения и пятикратный запас на результаты, повторы и служебные события дают около 4,3 ГиБ. При среднем запросе 2 МиБ тот же сценарий уже требует около 34 ГиБ. Поэтому 12 ГиБ не гарантируют семь суток для любой нагрузки. Настраиваем `retention.bytes` отдельно по топикам с учетом числа partition и запаса на активные сегменты, ограничиваем размер сообщений, следим за lag и диском. При длительном отставании останавливаем прием новых запусков до истечения срока хранения, разбираем накопившиеся запросы и проверяем, какие события можно восстановить из БД.

Шифрованные копии БД и файлов храним в другом аккаунте у независимого провайдера. Вместе с копиями сохраняем версии объектов, контрольные суммы, параметры топиков и версию релиза. Проверяем восстановление PostgreSQL и MinIO вместе, чтобы ссылки в БД не указывали на отсутствующие файлы. Для событий Kafka, которых нет в PostgreSQL, заранее решаем, как сохранить и восстановить нужные данные. Ключ записи копий не может их удалять; доступ для восстановления отдельный. Снимки VPS у того же провайдера не заменяют внешнюю копию. Реализация копий: [OVM-169](https://overmindv.atlassian.net/browse/OVM-169).

## Стоимость и регион

Вариант в России: Fatmetal, два VPS в одной зоне с частной сетью. Помесячные цены на 20.11.2026, стандартные CPU 2 ГГц. Перед заказом надо подтвердить наличие обоих тарифов в зоне `center-2`, способ оплаты и полный счет.

| Позиция | ₽ в месяц |
| --- | ---: |
| Приложение: Профи (6 CPU, 16 ГБ, 200 ГБ) | 2 200 |
| Runner: Старт (2 CPU, 4 ГБ, 50 ГБ) | 650 |
| Частная сеть | 200 |
| **Два VPS и сеть** | **3 050** |

[Тарифы VPS](https://fatmetal.ru/pricing/vps), [цена и зоны частной сети](https://fatmetal.ru/docs/private-networks#11--скорость-и-стоимость). По [курсу Банка России на 20.11.2026](https://www.cbr.ru/currency_base/daily/?UniDbQuery.Posted=True&UniDbQuery.To=20.11.2026) это около 34 евро: ориентир 30 евро превышен еще до бэкапов.

Для оценки внешнего бэкапа: в [примере тарификации Yandex Object Storage](https://yandex.cloud/ru/docs/storage/pricing) 100 ГБ в стандартном классе, 1 000 запросов записи и 10 000 чтений обходятся примерно в 235 ₽/мес. Тогда два VPS, сеть и хранение стоят около 3 285 ₽/мес, или 36,6 евро, без дополнительного трафика восстановления и комиссий. Это пример, а не утвержденный объем. Для бэкапа проверяем стоимость по своим данным, регион и поддержку [Object Lock](https://yandex.cloud/ru/docs/storage/concepts/object-lock).

Вариант в Казахстане: получить расчет на такие же два узла, сеть и отдельное хранилище копий, например у [PS.kz](https://www.ps.kz/ru/hosting/vps). Сравнивать полный месячный счет, а не цену младшего VPS. Решение о регионе, бюджете, SLO, RPO и RTO принимают Лео и Саша вместе. Если 30 евро окажутся жестким пределом, до запуска пересматриваем тарифы или объем пилота, не экономим на отдельном runner и внешней копии.

## Отказы и проверка перед запуском

| Отказ | Что произойдет |
| --- | --- |
| Узел приложения или его диск | Сайт и данные недоступны до восстановления. Горячего резерва нет. |
| Runner или связь между узлами | Материалы доступны. Проверки ждут восстановления в пределах очереди и политики повторов. |
| Единственный брокер Kafka | Отказ прерывает передачу запросов и вердиктов. Репликации между узлами нет. |
| Зона или аккаунт VPS | Можно потерять оба узла. Восстановление зависит от внешних копий и отдельного доступа к ним. |
| Публичный DNS или TLS | Пользователи не откроют сайт, даже если внутренние сервисы живы. |

На стенде проверяем полную конфигурацию из готовых образов: 10 одновременных пользователей, два слота Go/Python, перезапуск worker с очередью, прием и чтение файлов при обновлении ClamAV, восстановление из копий на чистом узле. Снимаем пиковую память, OOM и рестарты, заполнение диска, Kafka lag и время от отправки решения до вердикта. Прогон описан в [OVM-172](https://overmindv.atlassian.net/browse/OVM-172). Пока эти проверки не пройдены, не считаем конфигурацию достаточной для публичного запуска.

## Production Compose

На обеих VM нужны Docker Engine 28+, Compose 2.24.4+ и Python 3.12+. У Engine до 28
[loopback-порты могли быть доступны из локального сегмента](https://docs.docker.com/engine/network/port-publishing/).
Production overlay использует [теги слияния Compose](https://docs.docker.com/reference/compose-file/merge/).
Проекты `overmindv-production` и `overmindv-runner` имеют отдельные сети. Базы и бакеты
не берут данные из локальных томов `overmindv`.

| Узел | Порт на хосте | Куда передает прокси |
| --- | --- | --- |
| Приложение | `127.0.0.1:13000` | Frontend |
| Приложение | `127.0.0.1:18081` | Только `/graphql` |
| Приложение | `127.0.0.1:19000` | S3 API для браузерных запросов, без консоли |
| Runner | `127.0.0.1:15050` | Исполнение go-judge |
| Runner | `127.0.0.1:15051` | Компиляция go-judge |

На узле приложения внешние запросы принимает Caddy, см. раздел ниже. На runner прокси слушает
только частный интерфейс и принимает запросы только от узла приложения. Sandbox worker
использует отдельные HTTPS-адреса для исполнения и компиляции. До запуска нужно настроить аутентификацию между
узлами, firewall и TLS по [OVM-163](https://overmindv.atlassian.net/browse/OVM-163).
Compose не настраивает firewall VM и не доказывает изоляцию пользовательских процессов.
Контейнер go-judge привилегированный, поэтому его нельзя запускать на узле приложения.
На runner не передаем env-файл приложения, базы, ключи хранилища или Docker socket.
Отдельные bridge-сети не заменяют две VM. Если на Docker Engine уже есть сеть
второго production-проекта, скрипт откажется запускать контейнеры.
Оба контура начинают с одного слота. Второй слот включаем после испытаний.

На обоих узлах используем один `release.json` со ссылками по digest из OVM-165.
В релиз включаем Users с коммитом
[`0d4df88`](https://github.com/overmindv/users/commit/0d4df88c7d9b973f39c8c197574248d39768edd9)
или последующей версией без демо-сида. Миграции сервисов идут отдельными заданиями.
После миграции отдельное задание проверяет Users по прежним демо-ID и адресам из
локального сида. При совпадении API не запускается. Проверка не меняет записи.
Базу пилота готовим отдельно.

На узле приложения указываем путь к `001_init_runs.sql` из точного коммита Sandbox,
указанного в release manifest. Сохраняем байты из Git, без смены переводов строк.
Скрипт сверяет SHA-256. SQL монтируется read-only только в контейнер миграции.
Если набор миграций Sandbox изменится, скрипт потребует обновить этот порядок запуска.

Env-файл приложения держим вне репозитория под `root` с правами `0600`.
Родительские каталоги принадлежат root и не доступны другим на запись.
Команда `up` проверяет права до чтения env. `BOOTSTRAP_SUPERUSER_EMAIL`
и пароль задаются явно. `CORS_ORIGINS`, `MEDIA_S3_PUBLIC_ENDPOINT` и
`MEDIA_PUBLIC_BASE_URL` указывают HTTPS-адреса веб-входа и S3. Права сервисов
в MinIO задает отдельное задание. `SANDBOX_GOJUDGE_BASE_URL` и
`SANDBOX_GOJUDGE_COMPILER_URL` указывают на закрытые HTTPS-адреса исполнения и
компиляции. `SANDBOX_WORKER_ID` задает постоянное имя worker.

Из корня `infra` сначала проверяем конфигурацию и манифест:

```bash
# Runner VM
python3 scripts/production_compose.py runner check --manifest /etc/overmindv/release.json

# Application VM
python3 scripts/production_compose.py app check \
  --manifest /etc/overmindv/release.json --env-file /etc/overmindv/app.env \
  --sandbox-migration /etc/overmindv/001_init_runs.sql \
  --runner-tls-dir /etc/overmindv/worker-tls
```

`check` не печатает конфигурацию и не запускает контейнеры. Для запуска на готовом
стенде заменяем `check` на `up`: проверка повторяется, сборка на VM отключена.

В MinIO анонимно доступны только проверенные публичные WebP. Оригиналы,
карантин, тесты и артефакты закрыты. Media требует ClamAV, а renderer получает
свой образ `media-renderer` из манифеста и работает без сети и ключей S3.
Состояние брокера и топиков сверяем с OVM-164 перед выпуском.

## TLS для событий каталога

Для релиза с outbox OVM-138 добавьте `--catalog-kafka-tls-dir /etc/overmindv/catalog-kafka-tls`
к `app check`, а после проверки стенда к `app up`. Без флага текущий брокер не
переключается. Локальный Compose этот флаг не использует.

В каталоге вне репозитория нужны `broker.pem` (ключ в PKCS#8, сертификат с
SAN `DNS:kafka` и цепочка, `root:1000`, права `0640`) и `ca.pem` (CA без ключа,
`root:root`, `0644`). Каталог и его родители принадлежат root и закрыты для
записи группой и остальными. В закрытый `app.env` положите три разные строки из 32
случайных байтов в hex: `OVM_KAFKA_CATALOG_BROKER_PASSWORD`,
`OVM_KAFKA_CATALOG_ADMIN_PASSWORD`, `OVM_KAFKA_CATALOG_ENTITIES_PASSWORD`.
Не используйте пароли от других сервисов.

У одного брокера KRaft остаются прежние диск, cluster ID и топики. Служебные
порты доступны только внутри контейнера. Entities пишет через `kafka:9094`
в `catalog.activity.v1` и проверяет CA и имя брокера. Через старый `kafka:9092`
Feed пока читает каталог, но запись в него запрещена. Старые клиенты делят
права `ANONYMOUS`: они ограничены набором нужных топиков и групп из плана Kafka,
но не разделены по сервисам. Запись в `learning.goal.v1` также закрыта для
`ANONYMOUS`. Порты брокера не публикуются. Это переходное
подключение, а не TLS для всех клиентов.

Переключение одного брокера предполагает короткий перерыв: сначала provisioner
проверяет настройки существующих топиков и выдает ACL, затем стартует Entities.
При несовпадении настроек provisioner останавливается, не меняя настройки топиков.
На стенде проверьте `sh tests/catalog-kafka-live.sh`, чтение Feed и отправку
реального события через Entities. Не удаляйте данные Kafka при откате:
возвращайтесь к прежнему манифесту и конфигурации одновременно.

### Feed: переключение без сброса offsets

После проверки профиля Kafka каталога добавьте `--feed-kafka-tls` к `app check`
и затем к `app up`. Используйте образ Feed с поддержкой Kafka TLS. В закрытый
`app.env` добавьте отдельный `OVM_KAFKA_FEED_PASSWORD` из 32 случайных байтов в
hex. Пароль получают только брокер и Feed. Не меняйте `FEED_CONSUMER_GROUP`:
Feed возьмет зафиксированные offsets прежней группы на том же брокере.

Учетка Feed читает события каталога, задач и материалов; писать в Kafka не
может. Старый listener больше не дает читать события каталога и задач и не
пускает анонимных клиентов в группу Feed. Чтение материалов для старой группы
Recommendations пока остается доступным. Настройки остальных клиентов те же.

Для отката оставьте `--catalog-kafka-tls-dir` и замените `--feed-kafka-tls` на
`--feed-kafka-rollback`. Используйте образ Feed, который работал до переключения.
Job снимет только запреты чтения для прежней схемы Feed, не меняя offsets,
настройки топиков или запреты на запись. После проверки обычный профиль
каталога можно снова запускать без флага отката. Простое снятие флага TLS
не отменяет запреты в брокере.

### Sandbox: SCRAM для worker

С профилем Kafka каталога добавьте к `app check` и `app up`
`--sandbox-kafka-credentials-dir /etc/overmindv/sandbox-kafka`. В каталоге
вне репозитория два файла: `username` со значением `sandbox` и `password`
с отдельным паролем из 32 случайных байтов в hex. Оба файла должны быть
`root:10001` с правами `0640`; каталог и его родители принадлежат root и не
открыты на запись группы или остальных.

Worker читает CA и учетку из файлов и подключается к `kafka:9094` по
`SCRAM-SHA-256` поверх TLS. Job настройки Kafka получает только файл пароля
и учетку администратора, необходимую для создания SCRAM-записи. Ни Kafka
учетка, ни ее файлы не передаются в go-judge. Не меняйте
`SANDBOX_KAFKA_GROUP_ID` и топики: worker продолжит с прежних offsets.
Tasks по-прежнему пишет запросы и читает результаты через `kafka:9092`,
но этот listener больше не дает читать запросы или писать результаты от
имени worker.

Для отката оставьте профиль Kafka каталога и замените
`--sandbox-kafka-credentials-dir` на `--sandbox-kafka-rollback`. Используйте
прежний образ worker, который работал через старый listener. Job отзовет
SCRAM-учетку и снимет только переходные запреты Sandbox. Хранилище Kafka и
offsets сохраняются, профиль Feed не меняется.

### Content: TLS для публикации событий

С профилем Kafka каталога добавьте `--content-kafka-tls` к `app check` и `app up`.
В закрытом `app.env` задайте отдельный `OVM_KAFKA_CONTENT_PASSWORD` из 32 случайных
байтов в hex. Его получают только брокер и Content, не job миграции базы.
Используйте образ Content с поддержкой TLS в Parker и миграциями outbox
`00014` и `00015`. Дождитесь успешного выполнения `content-migrate` до запуска
сервиса. Прежний образ не умеет подключаться с TLS, а новый не запустится
в production через старый listener.

Топики и формат сообщений не меняются. История отправленных событий остается
в outbox: обновление не включает автоматическую очистку. Content пишет в четыре
топика из плана Kafka через `kafka:9094`. Запись в них со старого listener
блокируется, чтение Feed и Recommendations остается на прежних настройках
и consumer groups. Перед переключением проверьте на стенде доставку из
outbox и чтение обоими потребителями.

Для отката остановите все экземпляры нового Content. Оставьте схему базы
на месте. После истечения резервов верните незавершенные записи в очередь
под ролью обслуживания Content:

```sql
UPDATE outbox
SET status = 'pending', claim_token = NULL, lease_until = NULL
WHERE status = 'publishing' AND lease_until <= CURRENT_TIMESTAMP;
```

Перед запуском старого образа проверьте, что не осталось записей
`publishing`. Если Kafka приняла событие до остановки, а БД не успела
отметить его, возможна повторная доставка с тем же ID. Записи `exhausted`
остаются в БД и требуют разбора отдельно.

Верните прежний образ Content в manifest и замените `--content-kafka-tls`
на `--content-kafka-rollback`. Сохраните профиль Kafka каталога и флаги
уже переведенных клиентов. Брокер отзовет учетку Content, а job снимет
запреты записи в его топики. Одно снятие флага TLS запреты не отменяет.

## TLS между Gateway и Content

Для чтения материалов через Gateway передайте `--content-tls-dir` в команду
`app check` и затем в `app up`. Без этого параметра production Gateway не
подключается к Content. В локальном Compose настройка не нужна.

Каталог на узле приложения содержит три файла. Держите его вне репозитория в
каталоге root без записи для группы и остальных пользователей:

- `server.pem`: сертификат сервера с SAN `DNS:content`, владелец `root:root`, права `0644`.
- `server-key.pem`: ключ сервера, владелец `root:10004`, права `0640`.
- `server-ca.pem`: сертификат доверенного CA, владелец `root:root`, права `0644`.

Content получает сертификат и ключ только для чтения. Gateway получает только
CA, проверяет имя `content` и передает отдельный `CONTENT_GRPC_SERVICE_TOKEN`
из `app.env`. Токен генерируется из 32 случайных байтов в hex. Для ротации
пересоздайте оба контейнера после замены файлов; не переключайте соединение на
HTTP. Прямой публикации черновиков это подключение не открывает.

Для модерации задайте отдельный `CONTENT_GRPC_MODERATION_TOKEN` из 32
случайных байтов в hex. Он попадает только в Gateway и Content через TLS
overlay. Без ключа методы скрытия и восстановления отключены. Нужны
`CONTENT_ACTIVITY_ENABLED=true` и работающий Kafka. Перед включением
обновите Feed до версии, которая обрабатывает `material.withdrawn`
и `material.restored`.

`CONTENT_CONTRIBUTION_ENABLED=true` включает отдельный поток событий
редактуры после принятия правки. Нужен включенный `CONTENT_ACTIVITY_ENABLED`
и топик `KAFKA_CONTENT_CONTRIBUTION_TOPIC`, совпадающий с планом Kafka.
Content пишет в него; Feed и Recommendations не получают доступ на чтение.

## Публичный HTTPS

Caddy 2.11.9 ставим на узел приложения как системный сервис. Указываем два DNS-имени,
направленные на этот узел: веб и S3. Снаружи открываем TCP 443 и TCP 80 для
получения сертификата и перенаправления на HTTPS. Порты Compose остаются на
loopback. На runner этот Caddyfile не используем.

В `/etc/overmindv/edge.env` нужны только две настройки, с такими же значениями как
в `app.env`:

```dotenv
CORS_ORIGINS=https://learn.example.org
MEDIA_S3_PUBLIC_ENDPOINT=https://files.example.org
```

Передаем этот файл через `EnvironmentFile=/etc/overmindv/edge.env` в секции
`[Service]` systemd drop-in для Caddy. Копируем [правила Caddy](../deploy/caddy/public.Caddyfile)
в `/etc/caddy/Caddyfile`. Проверяем перед перезапуском:

```bash
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile \
  --envfile /etc/overmindv/edge.env
```

Caddy получает и обновляет сертификаты через
[автоматический HTTPS](https://caddyserver.com/docs/automatic-https). HTTP API
администрирования Caddy выключен. Изменение Caddyfile применяем через перезапуск,
а не через команду `caddy reload`. Ключи сертификатов остаются в каталоге данных
сервиса Caddy, не в Compose и не в Git.

Gateway работает в режиме `production` с Secure cookie и принимает
`X-Forwarded-Proto` только от адреса bridge gateway приложения. По умолчанию это
`172.29.163.1/32`. Если сеть пересекается с сетью провайдера или VPN, заранее
выбираем непересекающиеся `PRODUCTION_APP_BRIDGE_SUBNET` и
`PRODUCTION_APP_BRIDGE_GATEWAY`. Проверяем на целевой VM, что соединение от
хостового Caddy приходит именно с этого адреса. Не расширяем доверие до всего
подсета ради обхода проверки. Текущий Gateway считает квоту входа по IP
транспортного peer, поэтому за прокси IP-квота общая для пользователей.

Веб-вход убирает служебные actor-заголовки и формирует собственный
`X-Forwarded-Proto`. До S3 доходят только browser POST/PUT в quarantine и
GET/HEAD для оригиналов и вариантов, включая `public/verified/variants`. Для записи и preflight нужен
origin веб-сайта. Host и query подписанных запросов сохраняются, cookie и
браузерный bearer до S3 не доходят. Права и подпись проверяет сам MinIO.
В логах Caddy не сохраняются заголовки и URI запросов.

Локальная проверка использует временный CA и не требует DNS или публичного ACME:

```bash
python3 tests/public_edge_smoke.py
```

## Приватный TLS до runner

На runner используем [отдельный Caddyfile](../deploy/caddy/runner.Caddyfile).
Этот Caddy слушает частный IP на TCP 8443 для исполнения и 8444 для компиляции,
без HTTP и публичного ACME. В firewall разрешаем оба порта только с частного IP
узла приложения. Caddy проверяет IP соединения и клиентский сертификат.
Оба адреса пропускают `GET /version`, `POST /run` и чтение или удаление по ID
артефакта. `POST /file` разрешен только для исполнения. Запросы уходят на
`127.0.0.1:15050` и `127.0.0.1:15051` соответственно.

Передаем Caddy на runner отдельный `EnvironmentFile` через systemd:

```dotenv
RUNNER_TLS_HOST=runner.internal
RUNNER_BIND_IP=10.70.0.20
RUNNER_APP_IP=10.70.0.10
```

Имена и IP здесь пример. DNS `RUNNER_TLS_HOST` должен резолвиться в частный
адрес runner. В `app.env` указываем:

```dotenv
SANDBOX_GOJUDGE_BASE_URL=https://runner.internal:8443
SANDBOX_GOJUDGE_COMPILER_URL=https://runner.internal:8444
```

Используем выделенные CA для сервера runner и клиентов worker. Закрытые ключи
CA не размещаем на этих VM. Сертификат runner должен иметь SAN с именем
`RUNNER_TLS_HOST` и назначение `serverAuth`. Сертификат worker выпускаем с
`clientAuth`.

| Узел | Файлы | Доступ |
| --- | --- | --- |
| Runner | `/etc/overmindv/runner-tls/server.pem`, `server-key.pem`, `worker-ca.pem` | Каталог `root:caddy` с `0750`, файлы `root:caddy` с `0640`; go-judge их не получает |
| Приложение | `/etc/overmindv/worker-tls/runner-ca.pem`, `worker.pem`, `worker-key.pem` | Каталог `root:10001` с `0750`, файлы `root:10001` с `0640`; read-only mount только в worker |

Родительский каталог `/etc/overmindv` на узле приложения ограничиваем для
обычных пользователей. В `release.json` нужен образ Sandbox с коммитом
[`273583c`](https://github.com/overmindv/sandbox/commit/273583c7a27edbac47a6906e44b7164c0a4b6b1c)
или последующей версией с поддержкой `SANDBOX_GOJUDGE_TLS_*_FILE`.
Worker проверяет CA и имя сервера перед отправкой данных задачи. В
runner-контейнере нет ключа worker, доступа к БД или S3.

При ротации CA сначала добавляем новый CA в доверенный набор на принимающей
стороне, затем обновляем сертификат и ключ на отправляющей. Перезапускаем Caddy
после смены его ключа или доверенных CA, worker после обновления его файлов.
Старый CA убираем после проверки `/version` и контрольного запуска. Полная
проверка firewall и маршрута между VM остается частью приемки.

Локальный тест требует Docker и OpenSSL, создает временные сертификаты:

```bash
python3 tests/runner_edge_smoke.py
```

## Роли баз данных

У каждого сервиса отдельный экземпляр PostgreSQL с тремя ролями. В `app.env`
заполняем три разных случайных hex-пароля для каждой БД. Например, для Users:

| Переменная | Роль | Где используется |
| --- | --- | --- |
| `USERS_POSTGRES_ADMIN_PASSWORD` | `postgres` | Контейнер БД, первичная настройка и операции администратора |
| `USERS_POSTGRES_MIGRATOR_PASSWORD` | `overmind_migrator` | Миграции и выдача прав на созданные таблицы |
| `USERS_POSTGRES_PASSWORD` | `overmind_app` | Users и проверка на старые демо-аккаунты |

Те же имена с префиксами `ENTITIES`, `TASKS`, `FEED`, `TASK_HUNTER`,
`RECOMMENDATIONS`, `CONTENT`, `MEDIA` и `SANDBOX`. Каждый пароль генерируем
независимо, например в менеджере паролей как 32 случайных байта в hex.
Доступ к Docker daemon ограничиваем администраторами: ему доступны секреты,
которые переданы контейнерам через environment.

При первом запуске PostgreSQL создает роли на пустом томе. Миграции идут от
`overmind_migrator`: он не суперпользователь, но может создавать объекты и
устанавливать [доверенные расширения](https://www.postgresql.org/docs/17/sql-createextension.html)
в своей БД. После миграций задание `*-grants` дает приложениям права на данные,
без DDL, изменения истории Goose и удаления записей аудита Users.
Если роли на существующем томе отсутствуют, новый запуск не откроет API с
админским DSN. Подготовку такого тома делаем отдельно с бэкапом и проверкой
восстановления; ничего автоматически не очищаем.

### Смена пароля БД

Меняем один пароль за раз в согласованное окно. Сначала останавливаем затронутый
runtime или убеждаемся, что миграции не выполняются, в зависимости от роли.
Входим в нужный контейнер через локальный Unix socket под системным postgres:

```bash
docker exec -it --user postgres overmindv-production-users-postgres-1 psql -X -U postgres -d users
```

В psql выполняем [`\password`](https://www.postgresql.org/docs/17/app-psql.html)
для нужной роли, например `\password overmind_app`. Не указываем пароль в SQL,
аргументах shell или заявке. Обновляем соответствующую строку в root-only
`app.env` и запускаем `app up` по инструкции выше. Смена переменной
`POSTGRES_PASSWORD` сама по себе не меняет пароль в существующей БД.
Проверяем новое соединение и отказ входа со старым паролем. Старые соединения
не закрываются сменой пароля; перезапуск приложения обновляет его пул.
Если вход не восстановился, возвращаем предыдущий пароль через psql и его
защищенную копию в env, без отката базы.

На временном PostgreSQL проверяем права, миграции и смену пароля:

```bash
python3 tests/postgres_roles_smoke.py
```

## Доступ к MinIO

Задание `media-buckets` создает бакеты, закрывает анонимный доступ и привязывает
[политики](../deploy/minio/) к трем учетным записям. Анонимное чтение разрешено
только для проверенных публичных WebP. Задание не выдает root-ключ
Media или Sandbox. Если существующий ID состоит в группе, имеет лишние политики
или отключен, задание завершится ошибкой и не включит его снова.

| Переменные в `app.env` | Формат ID | Права |
| --- | --- | --- |
| `MEDIA_S3_ACCESS_KEY`, `MEDIA_S3_SECRET_KEY` | `ovm-media-<8 hex>` | Чтение, запись и удаление в `media-quarantine/uploads/*`, `media/originals/*`, `media/variants/*` и `media/public/verified/variants/*/*.webp` |
| `SANDBOX_TESTS_ACCESS_KEY_ID`, `SANDBOX_TESTS_SECRET_ACCESS_KEY` | `ovm-tests-<8 hex>` | Чтение в `sandbox-tests/sandbox-tests/prod/*` |
| `SANDBOX_ARTIFACTS_ACCESS_KEY_ID`, `SANDBOX_ARTIFACTS_SECRET_ACCESS_KEY` | `ovm-art-<8 hex>` | Только запись в `sandbox-artifacts/sandbox-artifacts/prod/runs/*` |

Media может отменять multipart и читать список частей только в
`media-quarantine/uploads/*`. Фоновая очистка в production отключена до
согласования сроков хранения. Для тестового стенда ее можно включить через
`MEDIA_ENABLE_UPLOAD_CLEANUP=true` в локальном Compose.

Для readiness Media отдельно разрешен `ListBucket` на `media`: операция
[`HeadBucket`](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadBucket.html)
проверяет это право. Оно не дает читать содержимое остальных бакетов.
Ключ чтения тестов не публикует новые suite. Публикацию и резервные копии
выполняем под отдельными ролями вне worker.

`MINIO_ROOT_USER` задаем отдельно, без префиксов рабочих ключей. Каждое значение
пароля MinIO генерируем независимо, 20 случайных байт в hex (40 знаков).
Не назначаем этим ID дополнительные группы или политики вручную.

### Ротация ключей MinIO

1. Генерируем новый ID с тем же префиксом и новый пароль, обновляем пару в
   защищенном `app.env`. Менять только пароль действующего ключа не нужно.
2. Выполняем `app up`. Сначала `media-buckets` создает новый ID, затем
   затронутый сервис запускается с ним. Проверяем запросы с новым ключом,
   в том числе загрузку и чтение для Media. Старый ID остается активен.
3. Для Media ждем истечения уже выданных подписанных ссылок и проверяем,
   что нет ожидающих загрузок со старым ключом. Отключаем старого пользователя
   через [`mc admin user disable`](https://docs.min.io/aistor/reference/cli/admin/mc-admin-user/mc-admin-user-disable/).
   Проверяем отказ старого ключа. Бакеты и объекты не удаляем.

Для отката до отключения достаточно вернуть прежнюю пару в `app.env`.
После отключения старый ID надо явно включить перед откатом. Операции
администратора выполняем локально на узле приложения, не открывая доступ
к MinIO Console. Смену root-пароля делаем отдельно в окно обслуживания с
перезапуском MinIO; рабочие ключи при этом не меняем.

Локальная проверка использует временный MinIO и `curl` с SigV4:

```bash
python3 tests/minio_credentials_smoke.py --benchmark
```

## Ротация токенов сервисов

Для каждого токена генерируем 32 случайных байта в hex. Токен одинаковый
на двух концах одного вызова, но не совпадает с токенами других связей или
паролями БД и MinIO. `app check` проверяет это без вывода значений.

| Переменная | Кто использует |
| --- | --- |
| `JWT_SECRET` | Users и Gateway |
| `TASK_HUNTER_INGEST_TOKEN` | Task Hunter и Tasks |
| `TASK_HUNTER_GATEWAY_TOKEN` | Gateway и Task Hunter |
| `FEED_GATEWAY_TOKEN` | Gateway и Feed |
| `MEDIA_GATEWAY_TOKEN` | Gateway и Media |
| `MEDIA_USERS_TOKEN` | Users и Media |
| `RECOMMENDATIONS_SERVICE_TOKEN` | Gateway и Recommendations |

Сервисы принимают один действующий токен на связь. На время смены приостанавливаем
затронутый вызов, обновляем одну строку в `app.env` и пересоздаем оба контейнера
через `app up`. Проверяем успешный вызов и отказ со старым токеном, затем
возобновляем обработку. При ошибке возвращаем предыдущую версию секрета и
перезапускаем оба конца. После смены `JWT_SECRET` пользователям потребуется
войти заново. Токены не передаем в аргументах команд и не выводим конфигурацию
через `docker compose config` на экран.
